# 飞书群聊接入、管理员与黑名单设计

日期：2026-10-15。状态：**群聊适配已实现，源码公开能力开关已开放；自动化验证已完成，真实租户验收待执行**。

本文是飞书群聊适配的设计与实现依据。它更新了早期 MVP 的范围：本轮正式支持普通管理员的审批、文件发送和黑名单管理，并包含聊天命令和本机 TUI。使用方式见[群聊使用说明](feishu-group-chat-guide.zh-CN.md)，验证证据与真实租户联调边界见[实现与测试报告](../reports/tests/2026-10-15-feishu-group-implementation.md)。

## 1. 本轮明确的需求

用户已明确：

1. 每个群有且仅有一个超级管理员；本机可修复缺失的超级管理员。
2. 普通管理员可以有多人，可以处理审批、使用 `/sendfile` 发送文件，也可以管理黑名单。
3. **普通管理员只能拉黑或解禁普通成员，不能操作超级管理员、其他管理员或自己。**
4. 群权限、黑名单、管理入口和实现边界需要一起记录，作为后续适配依据。
5. 其他渠道及飞书私聊的既有业务行为应保持兼容；本轮群权限不能自动套用到它们。
6. 用户明确授权：不用机械遵守项目原有的实现约束，由实现者选择更合适的代码结构和实现方式，先把原则记录到文档。

本文补充的实施默认值包括：超管负责管理员任免；管理员不能撤销超管或本机作出的封禁；被撤销的角色不会因解禁自动恢复；超管转移后的原超管成为普通成员；没有有效超管时暂停审批、文件发送和聊天侧管理。上述细节用于消除实现歧义，不代表旧版已经具备这些行为。

这项授权适用于本轮飞书群聊适配：项目旧文档中的目录安排、文件行数、分层模板、既有接口形状和开发形式作为参考，不机械作为实现限制。可以根据实际复杂度重构、合并或拆分模块，调整接口和数据模型，选择合适的实现手段；不需要仅因为偏离旧项目约束而再次请求确认。

## 3. 范围与路由

本轮包含：群聊接收开关、@bot 触发、配对、名册、固定角色、黑名单、文本审批、群文件授权、管理命令、最小管理 TUI、状态迁移、审计、模拟完整链路测试和真实租户验收清单。

后续再扩展：自定义角色及逐项授权界面、飞书群主／平台管理员同步、组织架构、thread/topic 独立会话、群审批卡片、完整审计浏览和导出。当前 TUI 已可查看最近 10 条审计。普通管理员是本轮正式角色，不属于预留能力。

群的作用域使用通用 route：

```text
<channelId>:<accountId>:group:<chat_id>
例如 feishu:default:group:oc_group
```

- 一个群 route 共享一个当前 Codex session；成员不各自建立 route。
- 不同机器人实例、账号、群分别隔离角色、名册、黑名单、审批和待处理附件。
- 用户身份取当前应用上下文中的稳定 sender ID，飞书优先使用 `open_id`。不能跨应用或账号把裸 ID 当作同一个人。
- 身份以 `routeKey + senderId` 判断；显示名、群内昵称和文本中自称的角色都不授予权限。
- Chat-Codex 管理员由本机／超管指定，不从飞书平台群主或管理员身份自动推导。

### 3.1 渠道开关

新建和既有飞书渠道均默认关闭群聊接收。有效接收能力由发布策略、adapter 支持和渠道实例 `capabilityOverrides.group` 一起决定。

入口：本机渠道详情，以及已配对飞书私聊的 `/group on|off`。隐藏别名 `/grop on|off` 保留；私聊命令无需先绑定 Codex session。群里的 `/group` 子命令用于群权限管理，不能修改整个机器人实例的接收开关。

关闭接收后静默忽略群消息，保留 route、信任、角色、黑名单、名册和 session 绑定。开启接收只允许群进入配对流程，不自动信任所有群。

### 3.2 @bot 与入站顺序

所有群消息、图片、文件和命令都必须 @机器人；@所有人不等于 @机器人。

```text
渠道／发布开关
  → 事件校验、去重、@bot 识别和纯数据映射
  → 已有黑名单检查（包括配对前安全命令）
  → 配对／登记／命令与任务权限预检
  → 获准普通消息才下载附件
  → 再次检查权限后写待处理池、入队或执行命令
```

未 @bot 的消息不进入 Bridge、不创建 route、不生成配对码、不写名册、不下载附件、不回复。未配对或被拉黑成员的新附件也不能先下载落盘再拦截。

当前 adapter 在调用 Bridge 前下载附件，需调整为延迟 materialize，或注入由统一权限服务提供的通用入站许可回调。adapter 不复制角色矩阵，也不直接读写黑名单文件。下载途中权限变化时，在入池／投递前重查，未获准资源清理临时文件，不交给 Codex。

### 3.3 渠道隔离与兼容性要求

本功能归属于飞书群聊适配，但任务队列、命令、审批、文件出站和状态存储需要中间件支持。**允许修改共享实现，要求其他渠道的既有业务行为保持兼容**；“没有副作用”是待验证的验收目标，文档阶段不宣称已经证明。

| 会话范围 | 本轮行为边界 |
| --- | --- |
| 明确启用本策略的飞书群聊 | 应用本文的角色、黑名单、群命令、审批和文件规则 |
| 飞书私聊 | 保留消息、附件、审批卡片和原命令语义；仅增加已明确的群聊接收开关管理能力，不增加群角色或 `/name` 门槛 |
| 微信 | 保留收发、配对、会话绑定、任务、审批、文件和进度策略，不引入群权限检查 |
| Terminal／其他已接入渠道 | 保留原交互；不因存在 group 会话或相同 sender ID 就自动适用飞书群规则 |
| Mock／fake 测试渠道 | 默认保持原测试语义；模拟本功能时显式注入群权限策略 |
| 后续新渠道 | 可以显式复用群权限模块，未接入时不自动改变行为 |

实现需满足：

- 在渠道注册或会话策略装配处明确选择适用范围；不要只凭 `conversation.kind === "group"` 给所有渠道安装本规则，也不要仅靠渠道实例 ID 的名称前缀推断渠道类型。
- 新增中间件 hook／策略对未接入渠道默认沿用原路径。已接入的飞书群缺少权限状态或校验失败时拒绝受限操作，不能因兼容默认值而意外放行。
- 管理员、黑名单、附件来源和发送许可都携带完整 route 作用域。相同 sender ID 出现在其他群、账号或渠道时，不继承当前群的封禁或角色。
- 群命令的编号要求、`/P` 限制、会话切换限制和文件权限只用于目标群；共享审批实现的重构不能顺带改变私聊、微信的合法命令和卡片决定语义。
- 群文件检查只作用于目标群的文件／媒体路径，不给微信、飞书私聊的 `/sendfile` 或自动长文本文件增加管理员要求。
- 群权限 schema 的迁移只更新相应群记录，不改其他渠道的信任、绑定、权限配置或登录态。一个群权限加载／迁移失败时，应隔离该能力或 route 并报告，不能使所有渠道无法启动。
- 群管理操作、开关关闭和单群异常不能清空其他 route 的队列、待审批、附件或会话，也不能中断飞书私聊及其他渠道的连接。
- 修改公共接口时同步适配已有调用者，以行为回归确认兼容；不把“接口没变”当作兼容性证明，也不以文件位于公共目录为由回避必要重构。

## 4. 配对、成员登记与上下文

### 4.1 群配对

1. 启动服务后，未配对群的成员 @机器人，群里收到不含配对码的引导。
2. 本机运行期 TUI／终端显示当前群的配对码和身份信息。
3. 用户在当前群发送 `@Bot /pair <code>`；成功者成为唯一超管，写入可信 route 与群权限记录。
4. 后续成员无需重复配对。重复 `/pair` 不覆盖当前超管，也不恢复被撤销的角色。

配对码仅运行期生成，过期或重启失效。启动前 TUI 只能展示已发现 route，不能发现新群或展示新的配对码。

本机可手动信任已发现的群，设置超管时必须明确选人，不能静默把最近发言人设为超管。没有有效超管的群显示“待配置超管”：普通已登记成员的文本任务可继续，但审批、文件发送和聊天管理暂停，由本机恢复；开放审批不能绕过此状态。

### 4.2 成员名册

群内提供 `/name <名称>`、`/name`、`/whoami`。名册按机器人实例、账号、群及 sender ID 保存；同一人在不同群可使用不同名称。

- `/name` 只修改本人展示名，不改变角色、配对或黑名单。
- 普通任务要求已配对且已登记；未知名称先提示登记，不投递任务。
- `/help`、`/name`、`/whoami`、`/pair` 可在配对前使用，仍须 @bot，且已有黑名单优先拦截。
- 展示名去首尾空白，限 1–24 个 Unicode 字符，不允许换行；控制字符、日志格式和 Markdown 均按展示场景安全处理。
- 群任务使用手工名册名称；没有名称时管理界面回退 ID，不能靠事件中的名称绕过登记。
- 私聊继续使用 ID 兜底，不要求 `/name`，也不主动查询通讯录补名称。

路径沿用：

```text
~/.chat-codex/state/channels/feishu/<channelId>/accounts/<accountId>/groups/<chat_id>/members.json
```

### 4.3 群内协作与日志

普通群任务进入 Codex 前加 `小黄说：...`，运行中补充加 `小黄补充：...`。前缀在命令解析后、投递前生成，不改写原始消息。私聊不加此前缀。

群会话允许多人协作，不按 sender 再加独占任务锁。任务、补充片段、附件、审批、文件发送都保留来源身份；不使用 route 的“最后发言人”替代原始发起人。

日志区分私聊／群聊，显示群名或群 ID、发言人名和必要 ID。群名缓存失败不阻断主流程；名册与权限独立。详见[名称与群名册设计](feishu-user-name-cache-design.zh-CN.md)。

## 5. 角色与权限矩阵

### 5.1 角色

- **本机操作者**：独立于飞书成员身份的受信管理入口，可任免管理员、设置／转移超管、修复状态、管理黑名单和群绑定。
- **超级管理员**：每群唯一，由配对或本机设置产生。具有管理员业务能力，并负责角色任免和权限策略。
- **普通管理员**：每群可多人，由超管或本机任命。固定拥有审批、发送文件、普通成员黑名单管理能力。
- **普通成员**：不必逐个存入权限文件；未命中其他角色或黑名单的成员按此身份判断。
- **小黑屋用户**：黑名单优先拦截。即使异常数据同时残留管理角色，也不能获得权限。

### 5.2 能力矩阵

所有群内能力仍受接收开关、配对、@bot 和各业务前置条件限制；本机操作不依赖 @bot。

| 操作 | 本机 | 超级管理员 | 普通管理员 | 普通成员 | 小黑屋 |
| --- | --- | --- | --- | --- | --- |
| 普通任务／补充 | 不通过群入口 | 是 | 是 | 是 | 否 |
| 帮助／本人登记／本人身份 | 管理页面 | 是 | 是 | 是 | 否 |
| 单次审批 | 受信本机入口 | 是 | 是 | 仅开放审批时 | 否 |
| `/sendfile` | 受信本机入口 | 是 | 是 | 否 | 否 |
| 查看当前群权限、管理员和黑名单 | 是 | 是 | 是 | 否 | 否 |
| 拉黑普通成员 | 是 | 是 | 是 | 否 | 否 |
| 解禁普通成员 | 是 | 是 | 有限制，见第 6 节 | 否 | 否 |
| 拉黑管理员 | 先撤职并封禁 | 撤职与封禁原子执行 | 否 | 否 | 否 |
| 任免管理员 | 是 | 是 | 否 | 否 | 否 |
| 切换审批策略 | 是 | 是 | 否 | 否 | 否 |
| 设置／转移／清空超管 | 是 | 本轮通过本机 | 否 | 否 | 否 |
| 换绑 session／解除信任 | 是 | 本轮通过本机 | 否 | 否 | 否 |

普通管理员不能任免同级、修改自己的角色或改变审批策略。成员自称“管理员”、修改 `/name` 或在提示词里要求绕过检查都不改变权限。

### 5.3 审批策略

本轮对外提供两种模式：

- `restricted` → `admins_only`：默认，超管和普通管理员均可审批。
- `open` → `any_non_blocked`：所有未拉黑成员均可单次审批。

开放审批只影响审批资格，不增加文件发送、拉黑、角色管理或策略修改权限。界面将默认模式写为“管理员审批（超管＋管理员）”，不再标为“仅超级管理员”。旧状态的迁移见第 10 节。

### 5.4 超管与管理员生命周期

- 任命管理员需要明确目标 ID；目标不能是超管、已拉黑用户或机器人。已是管理员时返回幂等结果。
- 撤销管理员后立即成为普通成员；不自动拉黑，既有已执行操作不回滚。
- 本机转移超管时，新超管不能在黑名单中；从管理员转为超管时移出管理员列表。旧超管默认成为普通成员，本机可再单独任命其为管理员。
- 清空超管仅供本机修复，立即进入“待配置超管”；不得通过重新配对抢占管理身份。
- 同一个 sender 不能同时出现在超管、管理员和黑名单的有效集合中。发现冲突按黑名单拒绝并提示本机修复，不静默授予更高角色。

## 6. 黑名单操作与生效规则

### 6.1 操作对象和层级

**用户已确认：普通管理员只能管理普通成员，不能拉黑超管、其他管理员或自己。** 目标校验在真正写入前执行，不能只依赖 TUI 列表是否隐藏选项。

| 操作者 | 拉黑 | 解禁 |
| --- | --- | --- |
| 普通管理员 | 只能是当前普通成员；不能是自己 | 仅普通成员，且封禁由普通管理员作出 |
| 超级管理员 | 普通成员；管理员需同时撤职；不能封禁自己或当前超管 | 可解除管理员、超管、本机作出的封禁 |
| 本机 | 可管理普通成员和管理员；当前超管须先转移或清空 | 可解除全部封禁并修复异常记录 |

补充默认规则：

- 普通管理员不能撤销超管／本机作出的封禁，避免低权限操作反向覆盖高权限决定。谁封禁、以什么角色封禁要入库。
- 普通管理员可解除另一普通管理员对普通成员作出的封禁，不要求必须由原操作者解禁。
- 历史封禁没有可靠操作者级别时，仅超管／本机可解禁。
- 超管拉黑管理员时，撤销角色与写入黑名单必须为一个原子操作；解禁后只恢复普通成员身份，不自动恢复管理员。
- 被拉黑用户不能自助解禁；黑名单用户发出的 `/help`、`/name`、审批、管理命令也静默忽略。
- 目标解析支持真实 @用户或显式 `open_id`，不按显示名模糊匹配。不把 `@Bot`、@所有人或多目标歧义当作一个有效用户。
- 本机可以为当前应用作用域的 ID 预先设置规则，但不宣称该 ID 已通过飞书成员 API 验证为实际群成员。

### 6.2 当前群内生效

黑名单仅属于当前 route，不把用户移出飞书群，不自动影响其私聊或其他群。更名不影响封禁。重复拉黑／解禁返回当前状态，不制造重复条目。

“立即生效”定义为权限变更成功持久化之后：

- 新消息、命令、审批和附件停止进入处理流程。
- 清理该 sender 尚未消费的群待处理附件；其他成员的附件保留。
- 该 sender 尚未投递的排队任务、补充片段在出队时再次校验并丢弃；混合批次按来源过滤，不能误丢其他成员内容。
- 以该 sender 发起的未完成文件发送，在出站前再次检查并拒绝。
- 撤职后的管理员也要在审批和文件出站前重查；只要已无相应权限，就不能沿用入队时的结果。

已进入 Codex 上下文的文本和已获批执行的动作不能声称被撤回。拉黑不自动中断整个群共享 turn；有权限的管理员可以 `/stop`，本机也可停止。发起人被拉黑后，该发起人任务产生的未完成审批不再允许正向批准，有权管理者仍可拒绝／取消。

并发边界以统一授权点为准：如果权限变更在审批／发送获得执行许可之前提交，后者必须拒绝；已经交给远端执行的操作不能保证撤回。审计记录授权版本和事件顺序，避免承诺不可实现的即时回滚。

## 7. 聊天命令与防绕过

### 7.1 正式命令

下表均省略群聊必须的 `@Bot` 前缀。私聊只开放渠道级 `/group on|off`，不接受群管理子命令跨群操作。

| 命令 | 可用角色 | 行为 |
| --- | --- | --- |
| `/help`、`/name [名称]`、`/whoami` | 未拉黑成员，允许配对前 | 帮助／本人登记／身份 |
| `/pair <code>` | 未拉黑成员，配对阶段 | 当前群一次配对 |
| `/group admins` | 超管、管理员 | 超管和管理员列表 |
| `/group policy` | 超管、管理员 | 当前审批策略和本人权限 |
| `/group admin add @用户` | 超管 | 任命管理员 |
| `/group admin remove @用户` | 超管 | 撤销管理员 |
| `/group block @用户` | 超管、管理员 | 按目标层级拉黑 |
| `/group unblock @用户` | 超管、管理员 | 按目标和封禁来源解禁 |
| `/group blocked` | 超管、管理员 | 当前群黑名单及可解禁范围 |
| `/group approval restricted` | 超管 | 管理员审批模式 |
| `/group approval open` | 超管 | 开放审批模式 |
| `/OK <id>`、`/NO <id>` | 满足当前审批策略者 | 单次审批／拒绝或取消 |
| `/sendfile <任务>` | 超管、管理员 | 带文件发送权限的任务 |

所有目标命令允许将 `@用户` 替换为一个完整 ID；@解析必须保留规范化 ID 元数据，不能把去掉 mention 后的显示名当作身份。

`/approve <id>`、`/deny <id>` 等兼容别名进入同一个审批 handler。`/group admin role ...` 和自定义权限配置暂不开放，不能当成成功的空操作。

### 7.2 其余既有命令

不能只保护 `/group` 而让旧命令绕过群权限。所有群命令统一进入能力判断，再调用既有 handler。

| 命令类别 | 本轮群内规则 |
| --- | --- |
| `/status`、`/stop`、`/cancel` | 超管和管理员；`/cancel` 操作群共享待处理项，帮助中说明范围 |
| `/model`、`/permission`、`/plan`、`/code`、`/default`、`/goal`、`/compact`、`/progress`、上下文刷新 | 超管；保留原命令的确认、忙碌和支持能力检查 |
| `/new`、`/use`、`/resume`、`/sessions`／跨会话详情、工作目录选择、`/debug` | 群内本轮不开放，使用本机管理入口 |
| 用户输入问题的回答命令 | 使用请求自身的允许回答者规则；黑名单检查优先，不能把回答当成审批 |
| `/P` 及会话范围审批别名 | 群内本轮不开放，提示改为单次审批，避免共享会话获得长期审批豁免 |
| 新增或未知命令 | 未显式列入群能力映射则拒绝；别名必须归一化后判断 |

自动创建群首个会话仍走明确的绑定流程；已有群会话的更换由本机处理。普通成员不能通过会话选择的数字回复绕过上述限制。

帮助按角色展示实际可用命令。普通成员无权限操作时给简短拒绝，被拉黑者静默；群里不输出其他群状态、本机凭证或无关会话信息。

## 8. 审批编号、并发和审计

- 审批通知展示短编号、操作说明和允许的决定；群聊本轮使用文字审批。
- `/OK <id>`、`/NO <id>` 必须将编号传到审批处理器，不能丢掉参数后选最新一条。
- 不带编号时，仅当前群恰好一个 pending 审批可兼容；多个时提示选编号，不能自动选择最新。
- 校验 route、运行实例／请求有效性、当前角色、黑名单、审批策略和允许的 decision。跨群或旧运行实例的编号不能复用。
- 默认超管和管理员可处理；开放审批才允许普通成员。黑名单、缺失有效超管、失效 route 均不能被开放审批绕过。
- 记录任务原始发起人和实际审批人，两者不能混用。只有取消类决定可用于处理已被拉黑发起人的遗留审批。

并发与失败处理：

1. 以 `approvalKey` 建立决策串行区，进入后重读当前群权限；同一审批只能有一个处理中决定。
2. 进入 `resolving` 后再向 Codex 回写；其他操作者得到“处理中／已处理”，不重复调用 adapter。
3. 收到确定成功后记录 resolved、decision、处理人和时间。
4. 明确尚未发出的失败可恢复 pending，并在重试时重新校验权限。
5. 远端是否接收不确定时标记结果待核实，等待协议通知或本机排查，不能盲目重试或宣称成功。
6. 服务或 transport 重启后使旧 pending 标识失效，不把落盘审计误当作仍有效的 Codex 审批请求。

当前同步 `decide()` 的防重复能力可复用；是否需要独立锁文件按实际状态机组织，但必须覆盖回写失败和多入口并发。文本入口、未来卡片入口和本机处理入口共用同一决策服务。

## 9. 附件、文件发送与权限撤销

### 9.1 群共享附件

只有通过 @bot、配对、登记和黑名单检查的附件进入群共享池。示例明确为：

```text
小黄：@Bot [上传图片]
李四：@Bot 解释一下
```

不带 @bot 的图片或文件不会被保存供后续成员消费。

- 按 route 共享，允许其他未拉黑且已登记成员消费。
- 最多 5 个，10 分钟过期；超出上限拒绝新增并提示说明处理意图。
- 每个附件保留 sender ID、显示名快照、message ID、收到时间和群内附件序号。
- 消费时再次检查附件来源是否已被拉黑；移除失效附件后，明确提示剩余数量。
- 明确提示“群聊共享待处理附件”，避免误以为是个人私有池。
- `/cancel` 清理群共享待处理项，仅管理员以上可执行；普通成员可以补文字消费或等待过期。

投递格式区分附件来源和本次指令发起人，例如“小黄发来的图片 1；李四说：解释一下”。图片沿用 `localImage`；普通文件沿用中间件 `localFile`，在适配 Codex 时转为本地绝对路径说明，不把文件内容直接粘入提示词。保存路径继续使用 `~/.chat-codex/uploads/`。

### 9.2 出站文件

超管和普通管理员均可 `/sendfile`，普通成员不能通过开放审批、提示词或文件引用绕过此限制。

授权必须至少发生两次：收到 `/sendfile` 时，以及最终文件准备上传／发送时。发送时使用原始任务发起人的身份、route 和 session，不能使用最新发言人或最新审批人的身份。

- 角色被撤销或发起人被拉黑后，停止尚未授权发送的文件；不把整个结果转发到另一个群或私聊。
- 最终文本可以按原对话继续投递；文件未发送原因只给必要说明，群里不泄露被拒文件的本机路径。
- `/sendfile` 的文件引用解析、路径／类型限制和上传错误处理继续适用。
- 图片等以本机资源形式输出的媒体也走同一文件授权边界，不能换一个媒体类型绕过。
- 文本与文件均优先 reply 原消息，失败时回退到当前群 `chat_id`，不改变 route。
- 每个文件记录 route、原始发起人、session、文件信息、授权版本、发送结果及飞书返回的消息 ID。

后续长文本自动转文件的适配也必须通过本节授权。普通成员的超长回复按文本预算投递，超出预算时保存本机完整原文并提示，由管理员另行显式处理；不能把普通成员任务的自动文件当作“系统发送”绕过角色限制。此分支须纳入两项功能联合验收。

## 10. 状态、迁移与单一写入者

### 10.1 群权限状态

路径沿用 `~/.chat-codex/state/bridge/group-access.json`。以下是已实现模型摘要，以源码类型为准：

```ts
type GroupApprovalPolicy = "admins_only" | "any_non_blocked";
type GroupActor =
  | { kind: "local" }
  | { kind: "sender"; senderId: string };

interface GroupBlockRecord {
  senderId: string;
  displayName?: string;
  createdAt: string;
  source: "pairing" | "command" | "tui";
  createdBySenderId?: string;
  blockedByRole?: "local" | "super_admin" | "admin" | "unknown";
  reason?: string;
}

interface GroupAccessRecordV2 {
  routeKey: string;
  channelId: string;
  accountId: string;
  conversationKind: "group";
  conversationId: string;
  superAdmin?: GroupPrincipal;
  admins: GroupPrincipal[];
  blockedSenders: GroupBlockRecord[];
  knownPrincipals?: KnownGroupPrincipal[];
  approvalPolicy: GroupApprovalPolicy;
  normalMessagePolicy: "mentioned_non_blocked";
  blockedUserBehavior: "silent";
  revision: number;
  botSenderId?: string;
  audit: GroupAuditEntry[]; // 最近 500 条，含操作 ID、actor、角色、来源、结果、revision
  createdAt: string;
  updatedAt: string;
}
```

`GroupPrincipal` 和 `KnownGroupPrincipal` 复用现有模型，保留 ID、名称、来源、添加人和时间。管理员采用固定角色能力；`reservedRoles` 仅作为旧数据备份，不自动激活自定义角色。旧的单一 `managementPolicy` 不能再替代能力及目标层级判断。

本机 actor 只能由受信 UI／服务装配注入；群消息正文、raw 字段或命令参数都不能伪造 `kind=local`。所有群管理操作都在服务端重读 actor 当前角色，不信任调用者自报角色。

### 10.2 旧状态迁移

- 文件 schema 升到 2，写前备份旧文件，使用原子替换；迁移失败保留原文件并阻止群能力启用。
- 保留 route、可信记录、名册、超管、黑名单、已知成员和 session 绑定。
- 旧 `super_admin_only` 映射为 `admins_only`，新 `admins=[]`：迁移时有效审批人仍只有原超管。后续显式任命管理员才增加审批与文件权限。
- 旧 `any_non_blocked` 保留开放模式；缺少有效超管仍进入待修复状态。
- 不把 `reservedRoles`、飞书平台角色、`knownPrincipals` 或成员名册自动变为活跃管理员。
- 旧封禁缺少操作者来源时标记 `unknown`，仅超管／本机可解除。
- 身份冲突、未知策略、未知新 schema、scope 不一致等不能静默改成允许；提示本机修复。
- 回退旧程序前恢复对应备份；不要求不理解 schema 2 的旧程序安全修改新文件。

### 10.3 并发和落盘

每个 route 的角色／黑名单修改串行执行，在同一临界区内检查操作者、目标、当前 revision，写入完整变更并递增 revision。失败时不返回成功；内存与持久化状态不能半更新。

并发场景必须覆盖“管理员正在拉黑的人被超管提升为管理员”：按提交时的实际身份重新判断，不允许使用旧的普通成员身份封禁新管理员。

Bridge 与同进程 TUI 共用一个 `GroupAccessService`。运行前配置 TUI 的写入也必须与运行实例互斥；另一个进程持有运行状态写入权时只读或提示到运行实例操作，不能由多个 file store 快照互相覆盖。本轮不为此引入新的远程管理协议。

### 10.4 审计

记录操作 ID、route、操作者 ID／当时角色、本机或聊天来源、目标 ID、动作、结果、时间及状态 revision。覆盖任免、超管转移、拉黑／解禁、策略切换、拒绝的越权尝试、审批决定和文件发送。

时间以 UTC 存储，界面按本机时区显示。显示名为快照，不是检索或权限主键；不记录 secret、token 或文件正文。已知成员列表和审计按项目的有界保留策略处理，黑名单命中日志节流，审计浏览界面可后续扩展。

## 11. 模块职责

以下是实现起点，模块名和路径可按第 1.1 节调整。应保持职责与验证边界清楚，不要求原样保留目录或类名；渠道兼容性按第 3.3 节验收。

| 模块 | 本轮职责 |
| --- | --- |
| `src/channels/feishu/group/` | 消息与 mentions 归一化、名称展示、群平台字段；保留目标 ID |
| `src/channels/feishu/feishu-adapter.ts` | 接收开关、@过滤、资源 materialize、reply／create；调用通用预检接口 |
| `src/group-access/` | 角色解析、能力矩阵、目标层级、状态变更、revision 和统一授权 |
| `src/bridge/group-message-gate.ts`（拟新增） | 普通任务、所有命令别名、配对前安全命令、黑名单的统一入口 |
| `src/bridge/commands/group-command.ts`（拟新增） | 群管理命令解析并调用服务；与私聊 `group-receive-command.ts` 分派 |
| `src/bridge/commands/group-name-command.ts` | 本人名称、身份，展示管理员与实际审批能力 |
| `src/bridge/route-queue.ts` 与 steering | 保存发起人，出队时重查角色／黑名单，混合补充按人过滤 |
| `src/bridge/inbound-media.ts` | 附件来源、共享池、黑名单清理和消费复查 |
| `src/approvals/` 与共享 resolution | 编号、当前权限、原子决策、失败状态、处理人审计 |
| `src/bridge/delivery.ts` 等出站入口 | 统一的群文件授权，防止不同媒体／自动文件路径绕过 |
| `src/state/` | schema 2、迁移备份、原子读写；不包含飞书 API 调用 |
| `src/cli/actions/` 与 TUI | 受信本机入口、角色和黑名单操作、信息展示；不直接改 JSON |

权限判断通过动作能力表达，例如 `group:approve`、`group:send_file`、`group:block_user`、`group:unblock_user`、`group:manage_admins`、`group:set_approval_policy`。先判断角色是否有能力，再判断是否能对这个目标操作。

`GroupAccessService` 至少提供读取详情、检查能力、任免管理员、设置／转移超管、拉黑／解禁、修改审批策略的方法。方法接收真实 actor 和 scope，不能仅提供一个无操作者参数的 `blockSender(id)` 供任意入口直接调用。

业务按实际职责组织，避免重复的权限判断和隐式共享状态。测试可以复用现有 `tests/unit/`、`tests/integration/`，也可根据实现边界重新组织；目录选择不替代对规则、异常路径和渠道兼容性的验证。

## 12. 本机 TUI 与交互

主入口：`聊天绑定列表 → 群绑定详情 → 群聊权限`。渠道详情保留群聊接收开关，并可提供该机器人下的群列表入口。

```text
群聊权限：研发协作群
  配对：已配对      会话：已绑定
  超级管理员：小黄 (ou_...)
  管理员：张三 (ou_...)、李四 (ou_...)
  审批：管理员审批（超管＋管理员）
  黑名单：2 人

  设置／转移超级管理员
  添加管理员／移除管理员
  拉黑成员／解禁成员
  切换审批策略
  返回群绑定详情
```

界面规则：

- 查看／选择用户同时显示名称、ID、当前角色；可选最近发言人或手输 ID。不依赖全量群成员／通讯录接口。
- 显示管理员和黑名单数量，详情显示封禁操作者与原因（如有）；普通管理员的群命令列表只展示其可操作对象。
- 超管转移显示原、新身份及原超管降为普通成员的结果；新角色授予、撤职并拉黑、解禁、开放审批等操作在提交前展示明确影响并确认。
- 聊天侧采用显式命令完成管理；为开放审批、任命管理员、撤职并拉黑管理员提供绑定 actor、route、目标、revision 的短时确认，不能被别人代确认，也不能借用 `/OK` 审批编号。
- 当前没有有效超管时突出恢复入口；管理员不能借这个状态接管超管。
- 运行前界面不展示新配对码；运行期配对码仅本机可见。
- 群权限修改走 actions → service → store；运行期写入遵守第 10.3 节的单一写入者规则。

## 13. 实施顺序与完成标准

| 批次 | 工作 | 完成标准 |
| --- | --- | --- |
| 1 | schema 2、固定管理员角色、权限矩阵、黑名单层级、状态迁移 | 纯策略和 store 测试覆盖角色／目标／来源组合，迁移不自动激活旧预留角色 |
| 2 | 群入口 gate、延迟附件下载、群命令、所有旧命令和别名检查 | 普通成员无法经命令或选择回复绕过；管理员仅能操作普通成员 |
| 3 | 审批编号和处理人、回写状态、文件两阶段授权、队列与共享附件复查 | 并发决策一次生效，撤权／拉黑后无新的受限操作 |
| 4 | TUI 管理页、角色任免、超管转移、策略和黑名单操作 | 本机可完整配置和恢复，运行态与界面一致，不覆盖其他进程状态 |
| 5 | 集成回归、真实飞书群聊验收清单、文档和发布开关 | 本机完整链路和其他渠道自动化回归通过；按用户最新授权开放源码入口，真实租户证据另行记录 |

本轮已完成策略、持久化、Bridge、假飞书 SDK 和 TUI 的自动化验证；三种真实身份与多个真实群的部署验收不能由这些测试替代。

## 14. 验收清单

以下为验收依据。执行情况与测试文件对应关系见[实现报告](../reports/tests/2026-10-15-feishu-group-implementation.md)；真实租户和独立长文本功能的联合验收仍待执行。本轮没有新增长文本自动转文件路径。

### 14.1 路由、@和配对

- 开关关闭或未 @bot 时，文本、图片、文件、`/help`、`/name`、`/pair` 均不创建新状态或下载资源。
- @所有人不能触发；不同机器人、账号、群之间角色、附件和审批不串用。
- 配对码只在本机出现；配对者成为唯一超管，重配不覆盖角色。
- 未配对安全命令遵守黑名单，普通任务不创建／切换 session。
- 名称变化、同名或冒充管理员不改变权限；私聊保持原行为。

### 14.2 角色、黑名单与管理

- 超管任命两个管理员后，两人均能审批和发文件；撤职后受限权限立即失效。
- 普通管理员能拉黑／解禁普通成员，不能操作自己、其他管理员或超管。
- 管理员不能撤销超管／本机封禁；旧来源不明封禁同样受限。
- 超管拉黑管理员时同时撤职；解禁只恢复普通成员，不自动恢复管理权。
- 黑名单成员不能任务、补充、审批、发文件、改名或执行管理命令；开放审批也不例外。
- 同时提升角色与拉黑时按提交状态裁决；未知 ID、重复操作、scope 错误、冲突身份和落盘失败有明确结果。
- 改名、重启、再次配对不解除封禁；单群封禁不影响其他群／私聊。
- 本机转移超管后角色不重复；无有效超管时审批和文件发送暂停，本机能恢复。

### 14.3 审批与任务

- `/OK <id>`、`/NO <id>`、兼容别名准确处理目标编号，多个 pending 时无编号被拒绝。
- 普通成员仅在开放审批时可单次审批；管理员不能切换审批策略或任免同级。
- 两人同时处理同一审批只回写一次；明确失败可受控重试，不确定结果不重复回写。
- 错群、失效实例编号、过期或已处理请求均被拒绝；保存真实处理人。
- 待处理审批遇到撤职／拉黑／策略变化时重查；被拉黑发起人的遗留请求仅能取消。
- 普通成员不能通过 `/permission`、`/P`、命令别名、数字会话选择或提示词绕过权限。

### 14.4 文件、队列与界面

- 普通成员 `/sendfile` 不入队；超管与管理员可正常发送，发送前撤职／拉黑则阻止上传发送。
- 普通成员后续发言不能成为管理员任务的文件授权人；其他人的审批也不转移文件发送资格。
- 超长文本自动转文件和图片资源输出服从相同授权，不以“系统文件”绕过。
- A @bot 提交附件、B @bot 说明可共享处理，来源和指令人分别保留；5 个上限、10 分钟过期正确。
- 黑名单新附件不下载，已入池附件和未投递补充被过滤；混合批次不误丢其他成员内容。
- TUI、聊天命令与持久化状态一致；重启保存角色和封禁，旧数据迁移不激活 `reservedRoles`。
- 真实飞书验证 @信息、reply／create、图片文件、角色命令、多人审批、断线重连和开关关闭；不依赖模拟测试宣布正式可用。

### 14.5 其他渠道兼容性回归

- 微信、飞书私聊和 Terminal 的普通对话、配对、会话绑定、执行中补充、停止、审批、文件和附件按各自既有支持范围回归，不被要求登记群名称或配置群管理员。
- 飞书私聊审批卡片、微信文字审批及原有审批别名保持合法决定集合和命令语义；群内禁用 `/P` 不影响原本支持它的其他会话。
- 默认 mock 行为不变；群权限测试显式启用策略。未接入策略的其他 group 渠道不会自动收到飞书群命令限制。
- 同时运行飞书群聊和其他渠道：群中拉黑某人后，其私聊或另一群不被封禁；角色和 sender ID 碰撞不产生跨 route 权限。
- 群权限加载失败、一次管理命令失败、群接收关闭时，其他渠道仍可收发，既有队列、pending 审批和附件保留。
- 重构共享审批／队列／出站接口后，分别测试目标群和未接入策略的调用者；群撤权检查不会导致私聊、微信文件发送被拒绝。
- 群数据迁移和回退不修改其他渠道记录，重启后的既有绑定与运行策略保持一致。
- 每个被修改的共享行为都说明影响面并提供对应测试；真实渠道尚未验证的部分单独记录，不能以“只改了飞书目录”或“编译通过”推导零影响。
