# 微信与飞书长文本投递及新版适配设计

日期：2026-10-15。状态：**长文本与通用发送恢复仍为设计草案**。后续微信 2.4.10 的协议差异已实施，见[新版协议进度](2026-10-15-weixin-2.4.10-protocol-implementation.zh-CN.md)；这不代表本文的分段／文件降级／最新上下文与恢复已完成。

## 1. 本轮决策

微信、飞书都补齐发送前的长度保护。推荐行为是：**短回复照常发送，长回复自动分段并提示一次，特别长的最终结果改发完整文件**。用户无需先同意分段，也无需要求 Codex 重新生成短回复。

用户观察本次任务运行约 5 分钟后报错，并补充怀疑正文过长。本轮优先处理这一场景。现有两端 `sendText()` 都没有分段，是已确认的缺口；但微信 `ret=-2 errcode=0 prepare failed` 没有唯一指向长度，仍保留上下文与服务端拒收的排查分支。详见[故障分析](2026-10-15-weixin-prepare-failed-analysis.zh-CN.md)。

本项目使用独立 adapter，不直接加载两个 OpenClaw 插件。新版适配指对照最新版选择性更新发送逻辑；更新参考包、更新运行时依赖和修复分段分别验收。

用户确认本轮完成标准包括 **Codex 协议与两端渠道一起适配**。2026-10-15 最新范围调整：微信针对新版协议做必要适配，不再为中途自然语言摘要或突破连续发送限制做专项适配；现有摘要行为保留，见第 6.1 节。Codex 消息与提问语义、微信长文本及通用可靠性、飞书原有适配范围继续保留。整体顺序以[协同适配计划](2026-10-15-codex-cli-adaptation-plan.zh-CN.md)为准，本次仅记录文档。

## 3. 用户看到什么

### 普通短回复

维持原消息，不加提示、段号或结束通知。

### 需要分段的回复

提示并入第一段，沿用项目的中间件提醒前缀。示例：

```text
【Chat-Codex中间件提醒】内容较长，将分 3 条发送。

（1/3）
这里是第一部分正文……
```

后两条分别为：

```text
（2/3）
这里是第二部分正文……
```

```text
（3/3）
这里是最后一部分正文……
```

只在完整正文到达投递层、确定需要分段之后提示。执行满 5 分钟、typing、任务开始或正文接近预算时都不提前发送长度警告。每次逻辑回复只提示一次；不另发“全部发送完毕”，最后一段编号已经表明计划末尾。

### 特别长的最终结果

**首版建议普通最终回复最多连续发送 8 段；预计超过 8 段时，在发送任何正文前改为一个 UTF-8 `.md` 文件。** 8 是本项目的交互阈值，不是平台限制。两个 adapter 已有文件发送能力，可复用。

```text
【Chat-Codex中间件提醒】回复较长，将以文件发送完整正文。
```

随后发送 `codex-result-<短编号>.md`。文件保存完整原文，不增加模型摘要，不截断内容。提示不提前声称文件发送成功；文件也失败时使用下述失败提示。文件和文字发送到同一账号、同一 route，不生成公开下载链接。

上传前仍须校验渠道的媒体类型与大小要求。文件超限时保留本机副本并提示，不能又退回数十、数百条文字连续发送。实施阶段核对两个文件接口的当前限制并补边界测试，不能把本地存储的 50 MiB 容量当作单文件可发送上限。

自动文件模式仅用于普通最终回复（包括后台 final）。命令、审批、用户输入问题和安全通知继续按原语义完整分段，不把重要操作说明藏进附件。它们必须由格式化层控制合理体积；异常巨大的此类消息需在本机显式报错并保留原文，不能静默丢尾或自动批准。

飞书群聊正式接入后，自动文件模式还须遵守[群聊文件授权设计](feishu-group-chat-design.zh-CN.md)：以原始任务发起人的当前身份判断，只有超管和普通管理员可发送文件，开放审批不授予文件权限。普通成员的回复仍可在文本预算内分段；超过预算则保存本机完整原文并提示，由管理员另行显式处理。角色撤销或拉黑后，尚未授权发送的文件须停止；不能用“系统自动文件”绕过角色检查。这一群聊分支列入两项功能的联合验收。

### 中途失败

停止后续正文，最多尝试一条短通知：

```text
【Chat-Codex中间件提醒】回复未完整送达，已确认发送 2/4 段。
完整正文已保存在本机，可在终端查看。无需重新执行任务。
```

“已保存”只在本地保存成功后出现。没有本地副本时改为“请在本机检查对应 Codex 会话的结果”；命令／进度等不一定有 Codex 结果，不使用这句话。请求超时且是否送达未知时，改为“已确认发送 2/4 段，第 3 段状态待确认”，不直接说第 3 段丢失。

API 成功响应在此表示平台确认接收，不等同于用户已读。通知本身也可能失败：它只尝试一次、不触发递归通知、不作为可靠性保证；终端始终显示投递状态和已成功保存的结果路径。对持续 `prepare failed`、明确限流或权限错误不追加同渠道通知请求，直接记录本机状态，避免继续放大失败。

## 4. 两个平台的长度预算

| 渠道／类型 | 已核实依据 | 建议初始预算与计算方式 |
| --- | --- | --- |
| 微信文本 | 上游通用入口声明 `4000`；本次没有找到可用于保证送达的官方统一字节上限 | 每段最终展示文本同时不超过 `4000` UTF-16 code units 和 `4000` UTF-8 字节；这是本项目额外保守策略 |
| 飞书 `post + md` | 官方发送／回复接口均标明富文本请求体上限 `30 KB`；明确超长码 `230025` | 实际序列化请求 JSON 不超过 `24000` UTF-8 字节，包含 `content` 的字符串转义、`msg_type`、`uuid`、`receive_id` 等；对 reply 和可能的 create 取较大者 |
| 飞书审批卡片 | 同样属于 `30 KB` 类别 | 检查完整卡片请求；超限进入原有文本审批回退，再使用分段保护，不能从中间切开卡片 JSON |

飞书普通 `text` 的官方上限为 `150 KB`，但项目当前文本走 `post`，不能套用该值。[发送消息](https://open.feishu.cn/document/server-docs/im-v1/message/create.md)、[回复消息](https://open.feishu.cn/document/server-docs/im-v1/message/reply.md)还说明样式会增加实际消息大小，因此 `24000` 是留余量的本地预算，也不是服务端保证。

预算必须包含提醒、段号、换行，以及为分段补充的 Markdown 围栏。`text.length`、汉字数和 JSON 字符串长度都不能代替 `Buffer.byteLength(serialized, "utf8")`。微信约 1,300 个汉字就可能达到本地 4,000 字节预算，不应在界面写成“微信最多 4,000 个汉字”。

初版采用内部默认值与可注入测试参数，不增加聊天设置命令。若后续暴露高级配置，降低预算可直接支持；提高预算须校验协议边界，不能通过配置跳过请求检查。

## 5. 分段算法与正文完整性

1. 对未加提醒的完整消息计算成本，能单条发送则原样返回。
2. 超出预算时优先按段落、换行、句子边界切分；单个超长段落／代码行再按 Unicode code point 切分，不拆坏 surrogate pair。尽量保留完整 emoji grapheme，单个 grapheme 本身过长时退回 code point。
3. 飞书优先保留完整 Markdown 块；长代码块可在段尾关闭围栏、下段重新开启并保留语言。表格尽量按行切，不为凑长度删除单元格。无法完整保留排版时优先保证正文与字节预算，不声称跨消息排版完全一致。
4. 原文切片与展示前后缀分开记录。原文切片按顺序拼接必须逐字符等于原文；不用 `trim()` 删除边界空白，新增提醒和围栏不写回原文副本。
5. 预先计算段数，把 `（i/N）` 和首段提醒一起纳入预算；段数从 9 增至 10 等变化需要重新计算。段数稳定后才发送，发送期间冻结边界和编号。
6. 根据最终计划选择分段或文件；不先发几段再突然改成文件。后续补发保留原计划，不把“剩余两段”重新编号为一个新回复。

失败后不默认对未知 `ret=-2` 进行反复二分试探；已经发出首段后也不修改总段数。飞书明确 `230025` 时记录实际请求大小并停止该计划，后续通过调整预算或文件模式恢复，避免用相同超长请求切换接口重发。

## 6. 顺序、节流与平台恢复

### 微信

**持续发消息的能力边界（2026-10-15 补充）：** 用户反馈历史上连续发送较多消息后就发不出去。核对官方 `2.4.10` 源码与[变更日志](https://github.com/Tencent/openclaw-weixin/blob/main/CHANGELOG.zh_CN.md)，未发现解除微信服务端发送限制、无限主动推送或主动刷新 `context_token` 的能力。`2.4.10` 主要修复 OpenClaw 宿主兼容；工具进度消息在 `2.4.4` 已加入，仍通过 `sendmessage` 发送，不能据此推断它不计入额度或不会被拒收。`run_id` 用于关联同一轮消息，typing 用于显示输入状态，都不能作为解除限制的凭证。

已实现的保护是出站串行、逻辑消息间默认 `1200 ms` 间隔、失败退避和进度失败冷却，微信默认 `/progress silent`，仅开放 `silent/brief`。当前节流包在整个重试流程外层，默认 `prepare failed` 还可能触发带 token／去 token 两轮共 6 次请求；后续应让每次实际请求都经过统一节流和总尝试预算。后续 2.4.10 协议批次补齐 ID／引用等兼容能力，没有改变此处的发送恢复策略。

这里需要分别处理**单条过长**和**连续消息过多**：分段解决前者，却会增加后者的请求数。最多 8 段是本项目控制刷屏的策略，不能解释为微信保证能连续接收 8 条；固定发送间隔也不代表服务端保证的安全额度。本轮没有证据可以承诺具体条数、固定上下文寿命或长期无人回复时仍可无限推送。既有 `ret=-2 prepare failed` 也不足以单独证明限流。

通用发送可靠性继续处理用户问题、审批和最终结果的投递，所有消息仍遵守同一渠道限制；普通进度沿用既有策略，本轮不新增微信摘要专用合并或额度机制。遇到明确限流时尊重服务端等待建议；连续原因不明的拒收则停止当前投递，保存关键结果并显示本机状态。新入站只提供更新上下文的机会，不承诺自动解除服务端限制；补发遵循下述有界恢复和 `/retry` 设计。真实验收还需记录接口结果与手机端实际可见结果。

- 文本、媒体 caption、审批文本都经过同一长度保护。当前媒体 caption 直接构造 TEXT item，实施时必须消除这个旁路。
- 每段及其重试都进入现有出站节流，保留默认最小间隔 `1200 ms`。同一回复顺序发送；不能将段数组放进 `Promise.all()`。
- adapter 在真正出队和重试时，按渠道实例、账号、会话、收件人获取最新有效入站上下文；保留原 route 与本轮 `run_id`。新的 `/fff` 只刷新该作用域的上下文，仍保持静默。
- 结构化保留 `ret / errcode / errmsg / HTTP 状态`。`prepare failed` 仍归为原因未确定；取消默认“带旧 token 一轮失败后，再去 token 完整重试一轮”。恢复预算见[故障分析 P0-D](2026-10-15-weixin-prepare-failed-analysis.zh-CN.md#p0-d有界恢复默认取消去-token-重试)。
- 同一分段的重试保持稳定 client ID；没有服务端幂等保证时不能承诺恰好一次。缺少可用上下文时保留结果并结束本次尝试，不让旧回复无限占住队列。

### 飞书

- 继续使用 `post + md`。每段引用同一原消息，保留当前聊天／话题语义；不把上一分段当成新的用户消息。
- adapter 内按会话串行发送，建议同一接收方最小间隔 `350 ms`，同时遵守消息接口 `50 次/秒、1000 次/分钟` 的应用额度；其他发送路径、补发和文件提示也计入预算。官方单用户、单群为 `5 QPS`，群内为机器人共享额度，故本地节流不能保证永不遇到限流。[接口限制](https://open.feishu.cn/document/server-docs/im-v1/message/reply.md)
- 分段各有不同 `uuid`；同一分段同一内容重试复用原 uuid，长度不超过 50。官方去重窗口为 1 小时，不把它扩展为跨重启、跨接口或无限期保证。[请求去重](https://open.feishu.cn/document/server-docs/im-v1/message/create.md)
- 收紧现有 reply 失败即 create 的逻辑：首版仅对已确认原消息撤回的 `230011`，且同一可信 chat 允许普通消息时启用 create 回退；没有原消息 ID 则直接 create。话题 route 无法保持原投递位置时不降级到群主聊天。
- `230025` 不做同内容 create 回退；`230020`／HTTP 429 有界退避；权限错误终止；网络超时及 `230049` 等未确定完成状态不立即换接口发送。部分成功时保留成功段的位置，后续只处理未确认段，unknown 必须先确认或提示重复风险。

本次 SDK 升级单独检查 `bundleDependencies`、`npm-shrinkwrap.json`、现有 axios／qs overrides，以及 `scripts/patch-bundled-lark-sdk.mjs` 对 SDK 元数据的修改；不能只改 `package.json` 后宣称适配完成。长文本实现不以该升级成功为前置条件。

## 6.1 阶段摘要的协议与渠道适配

**2026-10-15 用户最新决定：微信针对新版协议做必要适配，不再专门适配中途摘要，也不以摘要机制解决连续发送限制。** 本节原先的微信摘要专用低频合并、额度预算、草稿预览移植和限流对比实验退出本轮必做范围。

本节所指摘要是 Codex 工作中的自然语言说明，例如“已检查配置，正在确认发送失败的原因”。微信已有 `assistant.commentary → BridgeCommentaryDelivery → sendText` 链路；普通 brief 可投递，silent 通常抑制，Plan 模式另有既有策略。保留现有功能与用户偏好，本次仅改文档，不改变运行行为。

### 保留的协议语义与回归范围

| 消息 | 本轮范围 |
| --- | --- |
| commentary：进展说明 | 正确识别身份，与 final 分开；按既有策略回归，不新增微信摘要发送机制 |
| partial_answer：阶段性答案 | 继续适配完整消息投递与运行状态，防止混入 final 缓冲 |
| async／带问题的消息 | 继续适配及时显示、回答关联与非阻塞语义，不当作可丢弃进度 |
| final：最终结果 | 继续适配真实 turn 结束状态，并使用长文本／文件及通用失败保护 |

以上消息语义见计划 S1-A／S1-B；微信新版协议差异、最新上下文、正文长度、统一请求节流及有界恢复仍归 C1。飞书继续按 C2 原有范围执行。本次范围调整不取消长文本设计，也不引入工具进度新模式。

### 上游分析作为参考保留

完整依据见[OpenClaw 中途摘要到微信的分析](2026-10-15-openclaw-weixin-commentary-analysis.zh-CN.md)。宿主将 commentary 转为 preamble，再按策略选择草稿或独立摘要；腾讯微信 `2.4.10` 未接入可编辑草稿，正常回复显式关闭 block streaming，最终正文仍作为普通 TEXT 调用 `sendmessage`。

`run_id`、内部 `tool` 队列和 typing 均没有已确认的摘要免限流保证。原先拟议的“仅最终回复”与“少量摘要＋最终回复”对比实验不再列为实施门槛；既有摘要只做协议升级所需的回归。`prepare failed` 的长度、上下文与服务端拒收诊断继续属于通用发送问题排查。

## 7. 保存结果与恢复边界

最终正文在首次发送前保存至当前应用数据目录下的 `outbound-results/<routeHash>/<deliveryId>.md`，与入站 `uploads/` 分开，不写用户项目仓库。文件名不含账号、收件人或会话原始标识；目录与文件权限遵循本地私密数据约定，POSIX 分别使用 `0700`／`0600`，Windows 按平台适配。

保存包含正文、route/session/turn 关联、计划类型、分段范围和成功回执的最小记录；不存微信 token、飞书凭证或请求头。采用原子写入。复用故障分析提出的容量策略：7 天、每 route 最多 20 条、总量 50 MiB；清理可淘汰已过期／已成功项，容量仍不足时在本机明确告警，不能悄悄挤掉未到期失败结果。

保存失败时：普通分段仍可尝试投递，但标记“本地副本保存失败”；需要文件模式时不能继续假装附件可用，应显示本机错误及会话取回入口。输出超出存储容量时显式处理，不自动截断或无限扩容。

首版只提供终端中的投递状态、已保存文件路径及当前进程内的有界重试。**持久化记录不等于自动补发已经实现。** 新 `/retry` 命令、重启后续发、新入站自动补发单列后续阶段，恢复时必须重新检查原 route 的信任、账号和 session 绑定；从不重新运行 Codex。

## 8. 消息覆盖与审批

| 消息用途 | 长文本行为 | 提醒／恢复规则 |
| --- | --- | --- |
| 普通及后台 final | 分段；超过 8 段改完整文件 | 首段或文件前提示一次，保存原文，失败状态可见 |
| 命令、错误、安全通知 | 完整分段 | 不自动摘要，不自动文件化；失败在本机可见 |
| 已允许发送的 progress／commentary | 先沿用既有合并、节流和噪声控制，再做长度保护 | 分段不会打开被 suppress 的消息或扩大 progress 权限；同一批只提示一次，失败进入既有 cooldown |
| 媒体 caption | 使用与文本相同的预算与顺序 | 与对应附件作为同一个逻辑投递跟踪，避免 caption 重试导致附件重复上传／发送 |
| 审批、用户输入问题 | 先保留交互语义，再分段 | 可执行选项／回答指引放在最后；失败不改变 pending 状态，不自动接受、拒绝或过期 |

审批不能用字符串截断来实现。飞书卡片在发送前测量，超限时不发残缺卡片，回退到包含完整说明的文本计划。分段文本完全被平台确认前，不标记审批提示已完整展示；异常提前到达的批准／回答不能以不完整内容为依据，需要完成说明投递后再处理，终端仍可基于完整原文操作。

同一 pending approval 的重试保留稳定 deliveryId 和成功分段位置。需要调整 `sendApprovalUntilDelivered()`，避免每轮重新生成 ID 并从第一段重发；卡片改为文本后，同一轮不能再反复重试已知超长的卡片。明确拒绝／取消及现有权限校验保持原语义。

## 9. 代码边界建议

以下文件与字段是拟议接口，不表示已新增：

| 位置 | 职责 |
| --- | --- |
| `src/channels/text-delivery-plan.ts` | 纯函数：原文切片、提示、编号、Markdown 围栏和计划；接受 adapter 提供的成本函数，不硬编码平台名 |
| `src/protocol/channel.ts` | 通用 message purpose、稳定 deliveryId、可选分段回执和部分失败信息；Bridge 不识别微信／飞书业务码 |
| `src/channels/weixin/` | 微信预算、最新上下文、队列、API 错误分类、逐段 client ID；caption 合流 |
| `src/channels/feishu/` | 使用真实请求构造器计算成本、顺序队列、uuid、reply/create 分类、卡片超限回退 |
| `src/bridge/delivery.ts` | final 原文保存、文件模式编排、统一状态、一次性失败提示、审批投递进度；只读取通用渠道策略 |
| `src/state/outbound-result-store.ts` | 最小结果与回执记录、原子写入、容量／保留期，不承担平台 token 缓存 |
| TUI 状态与日志模块 | 区分任务完成与回复投递完成，显示已保存文件及失败阶段 |

为使 Bridge 在首次发送前选择文件模式，可在通用接口提供可选 `planTextDelivery(target, text, options)`；返回可序列化且无凭证的计划及原文范围，具体成本与分段细节由 adapter 决定。`sendText()` 仍有兜底计划生成，覆盖直接由 progress 等路径调用的场景；传入同一计划时不能再次分段。

消息用途由实际调用方显式传递，只有明确标为 final 才可触发自动文件模式；旧调用方缺少用途时仍做长度保护，但不能自行猜成 final。稳定 deliveryId 在逻辑投递建立时生成，重试沿用，不能在每次 API 调用时重新生成。

保持 `SendResult` 现有必填字段，添加可选 `deliveryId / messageIds / chunkCount`；聚合结果的 `messageId` 明确为第一段 ID，全部确认后才返回成功，完成时间取最后一段确认时间。部分失败抛出通用投递错误，带已确认段、失败段与 `failed/unknown` 状态。新逻辑不得把第一段成功当作完整回复成功。

每个逻辑投递记录用途、原文字符／UTF-8 字节数、最大请求字节数、计划类型、段数、确认位置、错误分类和尝试次数；微信附上下文来源／年龄。诊断新增字段不记录原正文、token 或完整请求体。原文副本属于受控结果存储，不进入普通日志。

## 10. 实施顺序与验收

1. **发送保护**：纯函数分段、首段提示、两端真实成本校验、caption 覆盖、顺序节流和错误分类；微信同步解决出队仍使用旧 target 的问题。
2. **结果完整性**：final 原文保存、超过 8 段的文件模式、部分发送回执、失败提示、TUI 状态，以及审批重试去重。前两步共同组成推荐首版，不把“提示用户”单独当作修复完成。
3. **新版兼容**：独立验证飞书 SDK `1.75.0` 与发布包；微信无损消息 ID 等协议差异另列任务。参考包新功能按实际需求进入，不引入 OpenClaw runtime。
4. **后续恢复增强**：按故障分析的方案增加 `/retry` 和重启后精确续发。未实现前，帮助文案不得承诺这些能力。

实现后至少验证：

- 短消息发送一次且完全不变；预算边界、提醒开销、9→10 段编号均正确。
- 7,337 个汉字、emoji、中文夹英文、引号／反斜杠、长代码块、长表格和超长单行；原文可逐字符重建，每次真实请求满足各自预算。
- 微信每段逐次节流、最新上下文按账号／聊天隔离；媒体 caption 无旁路；`ret=-2` 不被误报为长度或登录态错误。
- 飞书双层 JSON 转义按字节测量；`230025` 不转 create，`230011` 仅在保持 route 的情况下回退；超时不形成不受控重复发送。
- final 恰好 8 段时正常分段，9 段时从一开始使用原文文件；文件上传／发送失败、保存失败、磁盘容量不足均有明确状态。
- 第 3 段失败且前两段成功时，不重发前两段，不继续第 4 段；unknown 不当作明确未送达；失败提醒自身失败不递归。
- 同一 route 的两条长回复不会相互穿插；其他 route 仍可推进；进度不会饿死 final／审批，stop/解绑能够结束尚未发送的计划。
- 审批卡片超限回退、说明分段、最后一段操作指引、重复投递与 pending 生命周期回归；新增提示不出现在用户未允许的 progress 模式。
- SDK 升级的既有功能回归，以及 npm 打包后实际包含的 SDK／axios 版本验证。

实施阶段执行构建、必要的定向测试与全量 `npm test`，按项目规范写中文测试报告。真实微信与飞书验收分别包含短回复、长汉字正文、代码块、文件模式和中途失败；微信另测约 5 分钟任务及中途新入站。离线通过不能替代服务端送达验证。
